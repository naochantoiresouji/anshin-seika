# あんしん正価モデル リファレンスアーキテクチャ仕様書

本ドキュメントは、公的個人認証（JPKI）に基づくゼロ知識証明（ZKP）と、経済的インセンティブ設計（Financial WAF）を組み合わせたチケット不正転売抑止モデル「あんしん正価」の**リファレンスアーキテクチャ仕様書**です。

システム全体の信頼境界（Trust Boundary）、アクター間の責務分離、コアシーケンス、およびトークンの状態遷移ルールを定義します。

## 1. 概要・設計思想（Design Philosophy）

### 1.1 目的：ゼロ知識認証（JPKI-ZKP）と経済的インセンティブ（Financial WAF）の両立

従来のチケット不正対策は、「厳格な本人確認（KYC）によるプライバシー侵害・利便性低下」または「緩やかなアカウント認証による大量BOT・名義貸しの横行」の二律背反に陥っていました。

本モデルは、以下の2つの機構を統合することでこの課題を解決します。

1. **ゼロ知識認証（JPKI-ZKP）による「匿名の一意性証明」**:
マイナンバーカードの署名鍵を用い、個人属性（氏名・住所・生年月日・マイナンバー等）をサーバーへ一切送信することなく、「実在する1人の人間が当該興行セッションに対して正当に認証を行った」という事実（`Nullifier`）のみを暗号学的に証明します。
2. **Financial WAF による「経済的防御壁」**:
トークン発行時の少額決済・同額ポイント還元（200円決済・200pt即時付与）、同時アクティブ応募数の上限（最大3枠）、および当選確定を起点とする14日間動的ロックを組み合わせ、大量アカウント運用や組織的買い占めの資金効率・回転率を構造的に低下させます。

### 1.2 メカニズムデザインの原則：属性判別・恣意性の排除と合理的意思決定による不正抑止

本アーキテクチャは、運営者による事後的な監視や「誰が転売目的か」という主観的・恣意的な属性判別を行いません。また、利用者の道徳心や善意にも依存しません。

* **等しく小さな不便の割り振り**:
システムはすべての利用者に対して「等しく小さな手間と制約（カード読取、少額デポジット、枠上限、当選後ロック）」を課します。通常の観客（1〜数公演を申し込む個人）にとっては許容可能な微小なコストである一方、数百〜数千口を扱う大口・組織的転売業者にとっては、物理カード・端末・資金拘束のコストが口数に比例して増大します。
* **期待ROI（投資対効果）の破壊**:
不正行為を「規約で禁止する」のではなく、「実行すると経済合理性が合わなくなる（赤字化する）」状態へ誘導することで、自律的な抑止を実現します。

### 1.3 リファレンス仕様のスコープ（最小構成・単一応募・厳格適用ルール）

本仕様書は、特定の興行形態や事業者の個別都合に依存しない**最小構成のリファレンスモデル**を定義します。

* **最小単位の前提**: 「1公演 ＝ 1 `Session_ID`」「1トークン ＝ 1応募（単一応募）」を基本単位とします。
* **厳格適用ルール（救済ロジックの排除）**: 状態管理の複雑化と抜け穴の発生を防ぐため、認証後の条件違反（重複応募・ロック中・上限超過）に対する「サスペンド（保留）状態」や「自動待機キュー」は設けません。事後ゲート判定によって違反リクエストは即時破棄され、業務ルール（ロック維持・上限カウント）が例外なく厳格適用されます。
* **拡張性の分離**: 複数枚応募（同行者トークンの集約）や、事業者規約に基づくUX緩和（事前重複警告など）は、本リファレンスモデルを破壊しない上位レイヤーの拡張として `5. 実運用に向けた拡張ガイドライン` に分離して定義します。

## 2. システム境界とアクター定義（Trust Boundary & Actors）

### 2.1 アクター一覧と責務の分離

本システムは、認証処理（ステートレス）と業務台帳管理（ステートフル）を明確に分離した4つの主要アクターおよび2つの外部連携コンポーネントで構成されます。

| アクター / コンポーネント | 状態保持 | 責務と役割 |
| --- | --- | --- |
| **チケット申込者**<br>*(会員アカウント / 端末)* | クライアント | チケット販売基盤にアカウント（`会員ID`）を持ち、認証要求・抽選応募・リセール出品・会場入場を行う主体。発行されたトークンを端末にバインドして保持する。 |
| **認証実行者（カード保持者）**<br>*(ローカルZKP生成)* | ステートレス<br>*(ローカル処理)* | マイナンバーカードとPINを用いてローカル環境でJPKI署名およびZKP・`Nullifier` を生成する主体。申込者本人と同一の場合も、家族等の別人の場合もある。 |
| **ZKP認証基盤**<br>*(ステートレス検証器)* | **ステートレス** | 提出されたZKPの数学的正当性とJPKI証明書の有効性を検証し、検証済の「あんしんトークン（`Nullifier` + 連番 + 認証基盤署名）」を発行する。`会員ID` や抽選・ロック等の業務状態は一切保持しない。 |
| **チケット販売基盤**<br>*(業務台帳・制御)* | **ステートフル** | `会員ID` と発行済トークンの紐付け、200円決済・200pt付与、同時3枠上限、14日間動的ロック、抽選実行、リセール、および機種変更再バインドを管理する中核基盤。 |
| **決済代行**<br>*(外部連携)* | 外部 | トークン発行時の少額決済（200円）およびチケット当選時の本決済を処理する。 |
| **会場ゲート端末**<br>*(外部連携)* | 外部 | 公演当日、申込者の端末にバインドされたトークンの署名と有効ステータスを販売基盤と照合し、カード提示なしのパスフリー入場を許可する。 |

### 2.2 データの非連結性（Unlinkability）：個人属性の隔離と `Nullifier` の中立性

プライバシー保護とシステムの中立性を担保するため、データ構造に以下の制約を設けます。

1. **個人属性の完全隔離**:
JPKI証明書に含まれる氏名・住所・生年月日・性別・マイナンバー等の個人属性は、**認証実行者の端末ローカル環境内でのみ参照**され、ZKP生成後に即座に破棄されます。ZKP認証基盤およびチケット販売基盤のネットワーク上には一切送信・保存されません。
2. **セッション固有の `Nullifier` による名寄せ防止**:
トークンの一意性を識別する `Nullifier` は、以下のハッシュ関数によって生成されます。

$$\text{Nullifier} = \text{Hash}(\text{JPKI署名} \parallel \text{Session\_ID})$$



入力に興行固有の `Session_ID` が含まれるため、同一人物が同じマイナンバーカードを使用した場合でも、公演（`Session_ID`）が異なればまったく異なる無相関の `Nullifier` が生成されます。これにより、システム管理者であっても複数の公演を横断した個人の行動追跡や名寄せ（クロスセッション追跡）を行うことは暗号学的に不可能です。
3. **トークンの意味的中立性**:
ZKP認証基盤が発行するあんしんトークンは「当該 `Session_ID` において実在する1人分の認証が完了した」という**純粋な存在証明**のみを表します。トークン自体には業務ルール（ロック状態や利用制限など）を埋め込まず、すべての業務制御はチケット販売基盤側の台帳ロジックに集約します。

### 2.3 管理単位の切り分け（`Session_ID` 単位 vs `会員ID` 単位）

本アーキテクチャでは、プライバシー保護（非連結性）と不正抑止（業務統制）を両立させるため、制御対象に応じて管理単位を2つの軸に厳密に切り分けます。

* **`Session_ID`（公演セッション）単位で管理する領域**:
  * **重複認証・重複応募の防止**: 同一 `Session_ID` 内での同一 `Nullifier` の再発行・重複利用をブロックします。
  * **トークンの有効範囲（セッション境界）**: 落選時や公式リセール成立時に復元されたトークンは、発行時に紐づいた同一の `Session_ID` 内（同公演の2次受付・リセール等）でのみ再利用可能であり、他の `Session_ID` へ流用することはできません。


* **`会員ID`（アカウント）単位で管理する領域**:
  * **同時アクティブ応募枠の上限**: 1つの `会員ID` が同時に抽選結果待ち（`IN_LOTTERY`）にできる応募数は最大3枠までとします。
  * **14日間動的ロック**: いずれかの公演で当選確定（`WON`）した瞬間、該当 `会員ID` に対して14日間の新規応募・再認証制限が発動します。
  * **機種変更（再バインド）の年間上限**: 端末破損・機種変更に伴うトークン再バインド手続きの実行回数は、`会員ID` 単位で年間 $N$ 回までに制限されます。



## 3. コアシーケンス仕様（Sequence Diagrams）

本モデルのライフサイクルは、4つの独立したコアシーケンスによって定義されます。各シーケンスの詳細なメッセージフローおよび分岐条件は、`sequences/` 配下の個別ドキュメントを参照してください。

### 3.1 [01_zkp_auth_and_token_issuance](sequences/01_zkp_auth_and_token_issuance.md)：ゼロ知識認証およびあんしんトークン発行
マイナンバーカードを用いたローカルZKP生成から、ZKP認証基盤でのステートレス検証を経て、チケット販売基盤へ有効トークン（`UNUSED`）を登録するまでの基本フローです。

* **認証セッション発行とローカルZKP生成**:
  チケット販売基盤が認証リクエストID（`Req_ID`）と対象公演の `Session_ID` を発行し、認証実行者の端末ローカル環境でJPKI署名およびZKP・`Nullifier` を生成します。個人属性はローカルで破棄され、外部へ送信されません。
* **ステートレス検証**:
  ZKP認証基盤は提出されたZKPの数学的正当性とJPKI証明書の有効性のみを検証し、署名済みの「あんしんトークン（`Nullifier` + 連番 + 認証基盤署名）」を返却します。
* **事後ゲート判定と課金確定**:
  チケット販売基盤へのコールバック到達後、業務ルールに基づく**事後ゲート判定**（同一セッション内の重複確認・14日間ロック確認・同時3枠上限確認）を実施します。
  * **判定 OK**: 200円決済確定および200pt即時付与を行い、`会員ID + Session_ID + トークン` を1対1対1で台帳登録します（初期状態：`UNUSED`）。
  * **判定 NG**: サスペンド（保留）状態を持たず、トークンを即座に破棄（`EXPIRED`）し、所定のポイント変換処理のみを適用します。

### 3.2 [02_lottery_entry_and_cap](sequences/02_lottery_entry_and_cap.md)：抽選応募および同時3枠上限
発行済みの未消費トークン（`UNUSED`）を用いた抽選エントリー（単一応募）と、応募受理時の2段階ゲート制御を定義します。

* **パスフリー応募**:
  申込者はマイナンバーカードを再度かざすことなく、端末にバインドされた `UNUSED` トークンを提示して抽選応募を要求します。
* **ロック優先の2段階判定**:
  チケット販売基盤は以下の順序で厳格なゲート判定を行います。
  1. **第1段階（14日間動的ロック確認）**: 該当 `会員ID` がロック期間中でないかを確認します。ロック中であれば即座に応募を拒否します。
  2. **第2段階（同時アクティブ応募上限確認）**: 該当 `会員ID` の現在の抽選結果待ち（`IN_LOTTERY`）件数が3枠未満であるかを確認します。上限に到達していれば応募を拒否します。
* **状態遷移**:
  両判定を通過した場合のみエントリーを受理し、トークン状態を `IN_LOTTERY` へ遷移させ、アクティブ応募枠を `+1` カウントします（拒否時はトークンを `UNUSED` のまま維持します）。

### 3.3 [03_lottery_result_and_lock](sequences/03_lottery_result_and_lock.md)：抽選確定・当落分岐・14日間動的ロック
抽選バッチの確定に伴うトークン状態の分岐、ロック発動タイミング、および落選時のトークン復元ルールを定義します。

* **当選確定時の処理（14日間動的ロック発動）**:
  当選が確定したトークンは `WON` へ遷移し、アクティブ応募枠を `-1` 解放します。同時に、**当選確定を起点として該当 `会員ID` に対する「14日間動的ロック」を即座に発動**します。
* **落選確定時の処理（同一セッション内復元）**:
  落選が確定したトークンはアクティブ応募枠を `-1` 解放したうえで、状態を `UNUSED` へ自動復元し、優遇スコアを加算します。復元されたトークンは**発行時に紐づいた同一の `Session_ID`（同公演の2次受付・公式リセール等）内限定**で再利用可能であり、他公演への流用はできません。

### 3.4 [04_resale_and_venue_entry](sequences/04_resale_and_venue_entry.md)：例外処理・機種変更・リセール・会場入場
当選確定後または有効トークン保有中に発生する4つの独立イベント（未払いキャンセル・機種変更・公式リセール・当日入場および公演終了）の制御フローを定義します。

* **イベント1（未払いキャンセル）**:
  支払期限超過時、座席在庫は回収・再循環しますが、トークンは復元せず `EXPIRED`（失効）とします。**当選時に発動した14日間動的ロックは解除・短縮せず維持**します。
* **イベント2（端末破損・機種変更による再バインド）**:
  年間回数上限（年 $N$ 回）は **`会員ID` の機種変更手続き単位**で管理します。上限内であれば手続き枠を1消費し、保有中の有効トークン（各 `Session_ID`）ごとにJPKI再認証と `Nullifier` 照合を行います（同一のカード保持者であれば1回のカード認証で一括照合でき、異なるカード保持者の場合はカードごとに個別の認証操作を実施します）。照合完了後、200円決済・200pt付与のうえ、旧端末のバインドを強制失効して新端末へ付け替えます（トークン状態は維持）。
* **イベント3（公式リセール成立・出品者側）**:
  売買成立時、出品者へ代金精算を行い、トークンを**同一 `Session_ID` 内限定で `UNUSED` へ復元**します。ロック回避を目的とした偽装転売を防ぐため、**14日間動的ロックは解除せず維持**します（※リセール購入者側のフローは `02` と同一のため省略）。
* **イベント4（会場入場および公演終了）**:
  公演当日、会場ゲート端末にて端末バインド済トークンを検証（カード不要のパスフリー入場）し、`USED` へ遷移させて二重入場をブロックします。対象公演（`Session_ID`）終了後、該当セッションに紐づくすべてのトークンを `EXPIRED` へ遷移させ完全失効します。

## 4. 状態管理とデータモデル（State Machine & Data Model）

### 4.1 [あんしんトークン全ステータス遷移表](specs/token_state_transition.md)
あんしんトークンのライフサイクルを構成する全5ステータス（`UNUSED` / `IN_LOTTERY` / `WON` / `USED` / `EXPIRED`）、全11パターンの状態遷移マトリクス、およびシステムが遵守すべき4つの不変条件（セッション隔離・ロック不可逆性・終端不可逆性・端末1対1バインド）の詳細定義は、別紙仕様書 [`specs/token_state_transition.md`](specs/token_state_transition.md) を参照してください。

### 4.2 業務ルール・ハードキャップ一覧（14日間動的ロック・同時3枠上限・年 $N$ 回機種変更）
チケット販売基盤の業務台帳上で強制される主要な制御パラメータおよび適用ルールの一覧です。

| 制御項目 | 管理単位 | 設定値（リファレンス基準） | 発動条件・適用ルール |
| :--- | :--- | :--- | :--- |
| **トークン発行デポジット** | トークン単位<br>*(発行 / 再バインド時)* | **200円決済**<br>*(200pt即時付与)* | 認証完了後の事後ゲート判定OK時、および機種変更再バインド完了時に課金確定。ゲート判定NG（重複・ロック・上限超過）時は付与破棄・ポイント変換のみ適用。 |
| **1公演あたりの応募口数** | `Session_ID` × `Nullifier` | **1トークン ＝ 1応募**<br>*(単一応募)* | 同一 `Session_ID` に対する重複認証・重複応募は不可。落選・リセール復元後も有効範囲は同一 `Session_ID` 内に限定。 |
| **同時アクティブ応募上限** | `会員ID` 単位 | **最大 3枠** | ステータスが `IN_LOTTERY`（抽選結果待ち）のトークン数をカウント。`WON` 確定または落選確定時に `-1` 解放。 |
| **14日間動的ロック** | `会員ID` 単位 | **14日間**<br>*(期間中新規応募・認証不可)* | いずれかの公演で `WON`（当選確定）へ遷移した瞬間に発動。未払いキャンセルや公式リセール成立を経ても期間満了まで解除・短縮不可。 |
| **機種変更（再バインド）上限** | `会員ID` 単位 | **年 $N$ 回まで**<br>*(例：年1〜2回)* | 機種変更手続きの開始時点で年間回数を `+1` 消費。1回の手続き内で保有する全 `Session_ID` 分の `Nullifier` 再照合を実施。 |

## 5. 実運用に向けた拡張ガイドライン（Implementation Notes）

1章〜4章で定義したリファレンスアーキテクチャは、特定の興行形態や事業者の個別都合に依存しない「最小構成・単一応募・厳格適用」のコア仕様です。

実際の商用サービスへ導入する際は、興行の規模・販売形態やカスタマーサポート方針に応じた拡張が必要となります。ただし、いかなる拡張を行う場合でも、**「ZKP認証基盤のステートレス性」「`Nullifier` の中立性・非連結性」「1人1トークン原則」というコア構造には一切手を加えず、すべて上位レイヤー（チケット販売基盤側）の業務ロジックとして実装する**ことを基本方針とします。

---

### 5.1 興行形態に応じたセッション粒度・複数枚応募（同行者集約）の拡張方針

#### (1) セッション粒度（`Session_ID`）の設計柔軟性
リファレンス仕様では「1公演 ＝ 1 `Session_ID`」を基準としていますが、実運用では興行の希少性や運営方針に応じて `Session_ID` の発行単位（粒度）を柔軟に設定できます。

* **公演単位（基本形）**: 1公演ごとに個別の `Session_ID` を割り当てます。利用者は異なる日程・会場の公演ごとに個別のトークンを発行して応募できます。
* **日程・会場単位**: 同日開催の昼夜2公演や、同一会場の複数日程に共通の `Session_ID` を割り当てることで、「1日につき1公演まで」「同会場での重複当選不可」といった制御を、システム改修なしで自然に実現できます。
* **ツアー・大会単位**: 全国ツアー全体や国際大会の特定フェーズ全体に単一の `Session_ID` を割り当てることで、「期間中1人1回限り」の厳格な当選機会の平準化が可能です。

※いずれの粒度を選択した場合でも、$\text{Nullifier} = \text{Hash}(\text{JPKI署名} \parallel \text{Session\_ID})$ の計算式およびZKP認証基盤の実装を変更する必要はありません。

#### (2) 複数枚応募（同行者トークンの集約）
ペアチケットやファミリー席など、1回のエントリーで複数枚（2〜4枚等）の連番応募を受け付ける場合は、代表者1人の認証で複数枚を発行するのではなく、**「1人（1枚のマイナンバーカード）＝ 1トークン」の原則を維持したまま、複数人のトークンを束ねる方式**を採用します。

1. **個別トークン発行**: 代表者（申込者）および同行者全員が、それぞれのマイナンバーカードを用いて当該 `Session_ID` に対する `UNUSED` トークンを事前に発行します（各自の端末にバインド）。
2. **同行者紐付け（グループ集約）**: 代表者が抽選応募（`02`）を行う際、同行者のトークン識別子（または招待コード経由での承認）を紐付けてエントリーします。
3. **一括状態遷移と個別入場**:
   * **同時応募枠・ロックの適用**: 応募受理時および当選確定時は、代表者だけでなく**紐付けられた同行者全員の `会員ID` およびトークン**に対して、同時3枠カウント（`IN_LOTTERY`）や14日間動的ロック（`WON`）を一律に適用します。
   * **当日入場**: チケット分配の手間を省きつつ不正譲渡を防ぐため、公演当日は代表者・同行者がそれぞれの端末にバインドされた自身のトークンをゲートへ提示して個別に入場（`USED`）します。

### 5.2 事業者規約に基づくUX緩和（事前重複警告等）の設計余地

リファレンス仕様では、悪意ある自動化ツール（BOT）や組織的転売に対する防御（Financial WAF）を優先し、サスペンド廃止・事後ゲート判定での即時破棄という厳格適用ルールを採用しています。

一方で、一般利用者の操作ミス（「すでにロック期間中であることを忘れて再認証してしまった」「同時3枠の上限に達していることに気づかずカードを読み取った」等）による摩擦やサポート問い合わせを低減するため、チケット販売基盤側のUI/UXレイヤーにおいて以下の緩和策を追加することが可能です。

#### (1) 認証開始前のプリフライトチェック（事前警告・ブロック）
`01` のシーケンス（マイナンバーカードの読み取りおよびZKP認証基盤へのリクエスト）を開始する直前に、チケット販売基盤側で現在の `会員ID` の状態を事前照会し、以下の条件に該当する場合はUI上で警告を表示して認証フローへの遷移をブロックします。

* 該当 `会員ID` が現在「14日間動的ロック」の期間中である場合（ロック解除予定日時を明示）
* 該当 `会員ID` の同時アクティブ応募枠（`IN_LOTTERY`）が既に上限の3枠に達している場合
* 該当 `会員ID` が既に同一 `Session_ID` の有効トークン（`UNUSED` / `IN_LOTTERY` / `WON`）を保有している場合

※異なる `会員ID` 間で同一のマイナンバーカードが使用されたケース（家族カード流用や複数アカウントでの重複認証）については、プライバシー保護設計上、カード読み取り前には検知できません。したがって、**事前チェックを導入した場合でも、最終防衛線としての「認証コールバック後の事後ゲート判定（即時破棄・ポイント変換）」は必ず維持する**必要があります。

#### (2) デポジットポイントの運用設計
事後ゲート判定NG時に変換される200円相当のポイントについて、有効期限、利用対象範囲（チケット代金のみ、または関連グッズ・手数料への充当可否）、付与上限などを事業者の会員規約および資金決済法等の関連法規に合わせて設計します。

#### (3) 拡張時に禁止すべきアンチパターン（コア原則の保護）
実運用における利便性向上を目的とする場合でも、以下の拡張は本モデルの抑止力を根底から損なうため実装すべきではありません。

* **特例によるロック手動解除機能の実装**: カスタマーサポート権限等による「14日間動的ロックの個別解除」を許容すると、組織的転売業者による虚偽申告やクレームを介したロック回避の抜け穴となります。
* **端末バインドの複数台同時有効化**: 利便性のために同一トークンを複数端末で同時に有効（クローン状態）にすることは、スクリーンショットやアカウント共有による当日転売を許容することにつながるため禁止します。
